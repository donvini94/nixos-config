Implementation facts to check:
- Server catalog refresh attempts are at most once per 300 seconds when queried.
  Cache is bound to upstream URL and a private API-key fingerprint. Failed
  refreshes retain valid cached metadata; there is no maximum stale age.
- Catalog membership is used to reject unknown completion models. With neither
  live nor cached data, catalog-dependent requests return 503. Upstream auth is
  still used on actual requests; verify revocation semantics rather than assuming
  cached membership is equivalent to current authorization.
- Linux client refresh runs on activation and through a 15-minute user timer.
  Client cache is endpoint-bound. JSON output is also used for OMP's YAML file.
  Declared transport overrides existing transport; other providers/options are
  intended to survive. This is custom behavior, not native discovery.
- Hermes hooks surround upstream activation, which regenerates its environment.
  They retain UI-owned keys, apply declared values, remember declared key names,
  seed missing preferences, and set the coarse managed marker to false.
- Granular policy is in =/var/lib/hermes/policy=, seen as =/data/policy= inside
  the existing container. Config points into the Nix store; policy environment
  is a root-owned file. Do not mistake application-layer policy for hostile-agent
  isolation: inspect parent ownership, terminal/sudo capabilities and networking.
- Nix still installs the workspace instructions/SOUL through upstream activation.
  Not every application file has become UI-owned or seed-only.
- The one-time context-override migration ran during Alucard's first activation
  of this work. It is removed in =43f8f23=. No separate upstream Hermes legacy
  migration command was run; do not conflate the two.

* Challenge the design before accepting the code

For each custom module/script/function, identify the concrete requirement,
consumer, state owner and failure behavior. Consider standard tooling or an
upstream capability first. Classify it as keep, simplify, replace, delete, or
investigate; provide evidence and capability impacts for each recommendation.

Priority questions:
1. Should a custom inference proxy exist? Compare maintained gateways and native
   integrations against attribution, monitoring, privacy and portability needs.
2. Can native provider discovery replace the catalog cache and client generator?
   Alternatives were not adequately investigated before implementation.
3. Can an upstream-supported ownership interface eliminate the Hermes hooks?
   This wrapper fixes real behavior but creates another lifecycle to maintain.
4. Are retained n8n services/scripts actually needed, or compensating for a
   deployment choice? Preserve private routing, runner authentication, workflow
   behavior, consistent backups and monitoring when comparing alternatives.
5. Which host/user/Org-tree assumptions remain despite newly configurable n8n
   paths/network? What is necessary for a reproducible second deployment?

The implementing agent acknowledged that it moved to implementation before a
sufficient design comparison. Do not use its successful tests to defend the
architecture automatically.

* Risk and correctness review leads

These are questions, not confirmed exploits or proof of correctness:
- Full request/response logging: credentials, personal/business content, log
  permissions, retention, redaction and outbound observability exports.
- Ingress exposure/authentication: host loopback, Tailscale publication, bridge
  sockets, caller-header trust, forwarded credentials and upstream endpoints.
- Request/body limits, unbounded threads/memory, large catalogs, streaming,
  disconnects, timeouts, resource contention and dependency failures.
- Catalog staleness and revoked approvals; key rotation; malformed/partial data;
  empty catalogs; capability mapping; absent limits and cache-pricing semantics.
  Native clients use zero for missing cache rates to satisfy their schema; that
  is not evidence those rates are free. Provider billing stays distinct.
- Atomic rename is per file, not a transaction across client files. The updater
  lock only coordinates updater processes, not native UI/manual writers.
- Activation failure midway, concurrent Hermes writes, missing/stale snapshots,
  interrupted cleanup, ownership changes, symlinks and malformed nested state.
  Inspect dotenv quoting/interpolation and removal/rotation of managed keys.
- Policy-directory ancestry and mutability; whether UI, CLI, profiles and child
  processes all see the same policy; package update behavior after disabling
  the coarse lock; distinction between proxy policy and effective network access.
- Backup/restore completeness: do not assume a database backup covers filesystem
  artifacts, Hermes state, UI-installed packages or a container writable layer.
- README statements and comments may overstate ownership or coverage. Verify
  them against the implementation; do not create another duplicated inventory.

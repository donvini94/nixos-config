# Python craft standards for API/automation/glue code that must survive handover

Scope note: every practice below is sensible for a 200-line automation script unless explicitly flagged `[LIBRARY SCALE ONLY]`.

## Practices

### 1. Declare single-file script dependencies inline (PEP 723)
- **Rule:** If the deliverable is one file, put `# /// script` with `requires-python` and `dependencies` at the top and run it with `uv run script.py`; never rely on the ambient interpreter having the imports.
- **Failure prevented:** The handover script dies with `ModuleNotFoundError` on the client's machine, or silently runs against a different library major version than it was written for. PEP 723's motivation is exactly this: "there is no standard mechanism to define metadata for tools whose job it is to execute such scripts."
- **Source:** Ofek Lev, PEP 723 (PEP-Delegate: Brett Cannon) — https://peps.python.org/pep-0723/ ; uv implementation — https://docs.astral.sh/uv/guides/scripts/ . PEP 723: *"Script runners MUST error if the specified `dependencies` cannot be provided."*
- **Enforcement:** MECHANICAL — `uv run` refuses to run when deps are unsatisfiable; `uv add --script f.py 'httpx'` edits the block for you; `#!/usr/bin/env -S uv run --script` makes it executable.
- **Contested?** No. This is the current standard shape for single-file scripts and is normative (PyPA spec, not just a PEP).

### 2. Lock the environment and verify the lock in the deploy path
- **Rule:** Commit a lockfile (`uv lock` for projects, `uv lock --script f.py` for PEP 723 scripts) and use `--locked` / `UV_LOCKED=1` wherever the code is built or deployed so an out-of-date lock is a hard failure.
- **Failure prevented:** "Otherwise, every build is a lottery" — the client rebuilds six months later, gets different transitive versions, and the script breaks with no code change to blame.
- **Source:** Hynek Schlawack, *Production-ready Python Docker Containers with uv* — https://hynek.me/articles/docker-uv/ (*"enforce that lock file is in-sync with pyproject.toml"*; `UV_LOCKED=1`; *"I think that `--locked` / `UV_LOCKED=1` is more appropriate for deployment pipelines"*). Also Hynek, *Semantic Versioning Will Not Save You* — https://hynek.me/articles/semver-will-not-save-you/ (*"Pin your dependencies and their transitive dependencies to their exact versions … Otherwise, every build is a lottery."*). Lockfile standardisation: Brett Cannon, https://snarky.ca/why-it-took-4-years-to-get-a-lock-files-specification/
- **Enforcement:** MECHANICAL — `uv sync --locked` / `UV_LOCKED=1` exits non-zero on a stale lock. Also `uv lock --script f.py` emits `f.py.lock`.
- **Contested?** *Which* tool is contested, not the practice. Hynek: uv is "Python's finest workflow tool for my (non-scientific) use cases." Brett Cannon documents that uv, Poetry and PDM disagreed hard enough to force PEP 751 through three drafts; PEP 751 (`pylock.toml`) is the vendor-neutral fallback if you must not depend on uv.

### 3. Lower bounds in the manifest; never speculative upper bounds
- **Rule:** Express dependencies as lower bounds (`httpx>=0.27`) and pin exact versions only in the lockfile; block a *specific* known-broken release (`flask!=1.1.2`), never a whole major (`flask<2`), unless you have verified that major is broken.
- **Failure prevented:** A speculative `<2` cap silently freezes the client out of all future security releases and, in Python's flat package space, creates unresolvable version conflicts the client cannot fix. Hynek: *"your application will eventually be full of CVEs and you'll never learn about it"*; *"there's no practical way for them to remove your pin."*
- **Source:** Brett Cannon — https://snarky.ca/why-it-took-4-years-to-get-a-lock-files-specification/ : *"setting a lower-bound and **not** setting an upper-bound if you can help it."* Hynek Schlawack — https://hynek.me/articles/semver-will-not-save-you/ : *"Don't ever pin major versions, unless you know they're broken."*
- **Enforcement:** JUDGMENT (no linter reads intent behind a specifier).
- **Contested?** **Yes, and this is the sharpest live disagreement I found.** Poetry's documented behaviour contradicts both: `poetry add "django@^4.0.0"` writes `django (>=4.0.0,<5.0.0)` and `poetry add django@latest` writes an upper bound too (https://python-poetry.org/docs/dependency-specification/). Hynek names this directly: *"Some Python packaging tools have adopted npm's major-version pinning (`^`) by default, despite the lack of npm's security features and despite Python's flat package space. Make sure to unpin them by hand if possible."* Hynek also points at Henry Schreiner's *Should You Use Upper Bound Version Constraints?* for the long argument. If you use Poetry, you must fight its default.

### 4. Every outbound HTTP call carries an explicit timeout
- **Rule:** Pass `timeout=` to every HTTP call (a `(connect, read)` tuple when the two differ); a request without a timeout is a defect, not a style lapse.
- **Failure prevented:** The scheduled job hangs forever against an unresponsive IdP endpoint, holds its lock/slot, and nobody notices until the next audit. `requests` docs: *"By default, requests do not time out unless a timeout value is set explicitly. Without a timeout, your code may hang for minutes or more."*
- **Source:** `requests` Advanced Usage → Timeouts — https://requests.readthedocs.io/en/latest/user/advanced/#timeouts . `httpx` is the counter-example that proves the point: *"HTTPX is careful to enforce timeouts everywhere by default … raise a `TimeoutException` after 5 seconds of network inactivity"* — https://www.python-httpx.org/advanced/timeouts/
- **Enforcement:** MECHANICAL — `ruff` rule `S113` (`request-without-timeout`, flake8-bandit) covers both `requests` and `httpx`: https://docs.astral.sh/ruff/rules/request-without-timeout/
- **Contested?** No. Note the documented gotcha: the connect timeout applies *per IP address*, so a dual-stack unresponsive host can double the perceived timeout, and neither timeout is wall-clock.

### 5. Retries are opt-in, bounded, backed off, and idempotent-only
- **Rule:** If a call must survive transient failure, mount an explicit bounded retry (`total`, `backoff_factor`, `backoff_jitter`, `status_forcelist`) restricted to idempotent methods; never wrap a `POST` in a blind retry loop.
- **Failure prevented:** Two opposite bugs. (a) People assume `requests` retries — it does not: *"By default, Requests does not retry failed connections."* (b) A hand-rolled `for _ in range(5)` with no backoff turns a 429 into a self-inflicted DoS, and a retried non-idempotent call double-creates or double-deletes an identity. urllib3 defaults document both traps: backoff is *disabled* by default (`backoff_factor=0`), and `allowed_methods` deliberately excludes `POST`/`PATCH`.
- **Source:** `requests` Advanced Usage (§ retries, the `HTTPAdapter(max_retries=Retry(...))` recipe) — https://requests.readthedocs.io/en/latest/user/advanced/ ; `urllib3.util.Retry` reference — https://urllib3.readthedocs.io/en/stable/reference/urllib3.util.html (*"By default, we only retry on methods which are considered to be idempotent"*; *"By default, backoff is disabled (factor set to 0)"*; `RETRY_AFTER_STATUS_CODES = frozenset({413, 429, 503})`; `respect_retry_after_header=True`).
- **Enforcement:** JUDGMENT — no linter knows which of your calls are idempotent.
- **Contested?** No disagreement found on the shape; practitioners differ only on library (`urllib3.Retry` via `requests` vs `tenacity` vs `httpx` transport retries, which cover connection errors only).

### 6. Treat pagination as correctness, not polish
- **Rule:** Any list endpoint must be consumed to exhaustion by following the server's own cursor (`Link: rel="next"`, `nextPageToken`, `@odata.nextLink`); never act on page one and never trust a hand-built `?page=N` loop without a termination check.
- **Failure prevented:** The most dangerous silent bug in IAM automation: a deprovisioning or entitlement-diff script that sees only the first page reports "no orphaned accounts" because it never looked. GitHub's docs show the exact trap: *"`GET /repos/octocat/Spoon-Knife/issues` will only return 30 issues … even though the repository includes over 1600 open issues"* — with **no error**. Same doc notes `per_page` above the maximum is silently clamped: *"you may receive fewer results than you expect without any indication that the `per_page` value was reduced."*
- **Source:** GitHub REST API — *Using pagination in the REST API* — https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api
- **Enforcement:** JUDGMENT.
- **Contested?** No.

### 7. No bare `except:`; catch narrowly; chain with `raise ... from`
- **Rule:** Name the exception you expect; use `except Exception:` only at a deliberate top-level boundary; when re-raising inside a handler always use `raise NewError(...) from exc` (or `from None` when you are deliberately hiding the cause).
- **Failure prevented:** A bare `except:` swallows `KeyboardInterrupt` and `SystemExit`, so the operator cannot Ctrl-C the script, and it "can disguise other problems" — the classic hours-lost handover bug where a scheduled job reports success while doing nothing. Dropping `from exc` loses `__cause__`, so the traceback the client sends you no longer names the root cause.
- **Source:** PEP 8, *Programming Recommendations* — https://peps.python.org/pep-0008/ : *"A bare `except:` clause will catch SystemExit and KeyboardInterrupt exceptions, making it harder to interrupt a program with Control-C, and can disguise other problems … (bare except is equivalent to `except BaseException:`)"*, and *"Design exception hierarchies based on the distinctions that code catching the exceptions is likely to need, rather than the locations where the exceptions are raised."*
- **Enforcement:** MECHANICAL — `ruff` `E722` (bare-except, https://docs.astral.sh/ruff/rules/bare-except/) and `B904` (raise-without-from-inside-except, https://docs.astral.sh/ruff/rules/raise-without-from-inside-except/).
- **Contested?** No.

### 8. `subprocess`: argv list, `check=True`, `timeout=`, and no shell over interpolated data
- **Rule:** Call external commands as `subprocess.run([...], check=True, timeout=N)`; pass a list, never a formatted string with `shell=True`, and if you genuinely need a shell, quote every interpolated value with `shlex.quote()`.
- **Failure prevented:** Two distinct failures. (a) Shell injection: the stdlib is explicit that *"If the shell is invoked explicitly, via `shell=True`, it is the application's responsibility to ensure that all whitespace and metacharacters are quoted appropriately to avoid shell injection vulnerabilities."* In IAM scripting the interpolated value is typically an attacker-influenced username or DN. (b) Silent failure: *"By default, `subprocess.run` does not check the return code of the process it runs. This can lead to silent failures"* — the `ldapmodify`/`az`/`gcloud` call fails, the script exits 0, the audit trail lies.
- **Source:** CPython docs, `subprocess` → Security Considerations — https://docs.python.org/3/library/subprocess.html#security-considerations (also: *"Providing a sequence of arguments is generally preferred, as it allows the module to take care of any required escaping and quoting"*). Silent-failure framing from `ruff` `PLW1510`.
- **Enforcement:** MECHANICAL for the missing check — `ruff` `PLW1510` (https://docs.astral.sh/ruff/rules/subprocess-run-without-check/); flake8-bandit `S602`/`S603`/`S607` flag shell use and partial paths. JUDGMENT for whether the interpolated value is trusted.
- **Contested?** No.

### 9. Never unpickle data that crossed a trust boundary
- **Rule:** Use JSON (or another non-executing format) for any cache, state file, queue payload or API response you did not just produce yourself in the same process; if `pickle` is unavoidable, HMAC-sign the bytes and verify before loading.
- **Failure prevented:** Remote code execution from a writable cache file or a message a client's ops team can touch. The stdlib is unambiguous: *"The `pickle` module **is not secure**. Only unpickle data you trust. It is possible to construct malicious pickle data which will **execute arbitrary code during unpickling**."*
- **Source:** CPython docs, `pickle` — https://docs.python.org/3/library/pickle.html (and: *"Consider signing data with `hmac` if you need to ensure that it has not been tampered with"*).
- **Enforcement:** MECHANICAL — `ruff` `S301` (suspicious-pickle-usage, https://docs.astral.sh/ruff/rules/suspicious-pickle-usage/), CWE-502.
- **Contested?** No.

### 10. Secrets never appear in source, and never appear in logs
- **Rule:** Read every credential from the environment or a secret store; and before logging any object, ensure it cannot carry a token, session identifier, password, connection string or key — log a stable identifier or a hash instead.
- **Failure prevented:** The IAM-specific catastrophe: a debug line that dumps the full API response or request headers writes a bearer token into the client's log aggregator, where it is retained, replicated and searchable by people who were never in scope for that credential. OWASP's exclusion list names precisely the fields IAM code handles: *"Session identification values … Access tokens … Authentication passwords … Database connection strings … Encryption keys and other primary secrets."*
- **Source:** OWASP Logging Cheat Sheet, *Data to exclude* — https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html . Hardcoded-secret side: `ruff` `S106` — https://docs.astral.sh/ruff/rules/hardcoded-password-func-arg/ : *"store passwords and other secrets in configuration files, environment variables, or other sources that are excluded from version control"* (CWE-259).
- **Enforcement:** MECHANICAL for hardcoded literals — `ruff` `S105`/`S106`/`S107`. **JUDGMENT for logs** — no linter can tell that `log.info("resp=%s", resp.json())` leaks a token. This is the single highest-leverage prose rule in this list for the user's domain.
- **Contested?** No. OWASP additionally notes to sanitise CR/LF out of logged values to prevent log injection.

### 11. `print()` is for the tool's output; a logger is for diagnostics
- **Rule:** Write the script's actual result to stdout with `print()`; route progress, warnings and errors to a named logger (`logging.getLogger(__name__)`) on stderr; go structured (key–value / JSON) only once something other than a human reads the logs.
- **Failure prevented:** Two symmetric failures — a script whose only diagnostics are `print()` cannot be silenced or levelled by the client's scheduler, and a script that logs its *results* through `logging` cannot be piped into `jq`. The stdlib settles this: `print()` is the best tool for *"Display console output for ordinary usage of a command line script or program"*, while a logger's `info()` is for *"events that occur during normal operation of a program (e.g. for status monitoring or fault investigation)"*.
- **Source:** Python Logging HOWTO, *When to use logging* table — https://docs.python.org/3/howto/logging.html . Structured side: Hynek Schlawack, structlog *Why…* — https://www.structlog.org/en/stable/why.html quoting Paul Querna: *"The first level consumer of a log message is a human. The programmer knows what information is needed to debug an issue. I believe these presumptions are **no longer correct** in server side software."* And structlog *Logging Best Practices* — https://www.structlog.org/en/stable/logging-best-practices.html : *"A simple but powerful approach is to log to unbuffered standard out and let other tools take care of the rest"*, plus the documented `sys.stderr.isatty()` split (pretty locally, JSON in production).
- **Enforcement:** JUDGMENT.
- **Contested?** Partly — the stdlib HOWTO blesses `print()` for CLI output where a naive reading of "never print, always log" would not. For a 200-line script, stdlib `logging` + `basicConfig` is the right handover default; `structlog` earns its dependency when logs are aggregated. Hynek's own bar for a dependency (practice 17) applies to `structlog` too.

### 12. Fixed-shape data gets a named class, not a dict or a tuple
- **Rule:** Model any record with a known set of fields as a `@dataclass` (stdlib default) rather than a dict or tuple; reach for `pydantic` only at the boundary where untrusted input is parsed, and do not let it leak into your domain objects.
- **Failure prevented:** `customer[2]` and `d["frist_name"]` — typo bugs that a class turns into an `AttributeError` at the point of the mistake, and tracebacks/`repr`s that the next maintainer can actually read. Hynek: *"if your dict has a fixed and known set of keys, it is an object, not a hash"*, and tuple unpacking means *"adding additional data means that you have to change the invocation of that function everywhere."*
- **Source:** attrs, *Why not…* (authored by Hynek Schlawack) — https://www.attrs.org/en/stable/why.html — covering dicts, tuples, `namedtuple`s, hand-written classes, dataclasses and pydantic.
- **Enforcement:** JUDGMENT.
- **Contested?** **Yes, and it is a real split.** Hynek argues pydantic is *"first and foremost a data validation & type coercion library"* and that using it for your domain layer *"is problematic in several ways: Is it really necessary to re-validate all your objects while reading them from a trusted database? Should the shape of your web API really apply design pressure on your business objects…?"* — pydantic is *"the right tool for Commands"* only. The mainstream FastAPI-influenced practice is the opposite: pydantic models everywhere. Hynek also concedes dataclasses are *"a fine library"* and that `attrs`'s advantages (validators, converters, `slots` consistency) *"depend on your circumstances"* — for a handover script with a non-expert maintainer, stdlib `dataclasses` wins on zero-dependency grounds even by Hynek's own criteria.

### 13. Annotate the boundaries; do not chase `--strict` on a script
- **Rule:** Type every function signature and dataclass field at module boundaries and where data changes shape; do not add annotations to local variables the checker already infers, and do not gate a 200-line script on `mypy --strict`.
- **Failure prevented:** Both over- and under-typing. Untyped signatures mean the next maintainer cannot tell whether `groups` is a list of strings or of objects without reading the whole file. Conversely, `--strict` on glue code that calls untyped vendor SDKs produces a wall of `import-untyped` errors and a culture of blanket `# type: ignore`, which is worse than no checking. mypy's own guidance is gradualist: *"even a little annotation coverage is useful"* and *"Prioritise annotating widely imported modules."*
- **Source:** mypy, *Using mypy with an existing codebase* — https://mypy.readthedocs.io/en/stable/existing_code.html (*"An excellent goal to aim for is to have your codebase pass when run against `mypy --strict`"* — framed as a goal for a *codebase*, alongside *"Strongly recommend enabling this one as soon as you can: `check_untyped_defs = True`"*). PEP 484 sets the ceiling: *"Python will remain a dynamically typed language, and the authors have no desire to ever make type hints mandatory, even by convention"* — https://peps.python.org/pep-0484/
- **Enforcement:** MECHANICAL, tiered. Script/glue: `check_untyped_defs = True`, `warn_unused_ignores = True`, `strict_equality = True`, plus per-module `ignore_missing_imports` for untyped SDKs. `[LIBRARY SCALE ONLY]` the full `--strict` set (`disallow_untyped_defs`, `disallow_any_generics`, `warn_return_any`, `no_implicit_reexport`, `extra_checks`) — mypy documents them as a ladder you climb, and `no_implicit_reexport` has *"lower"* return on investment by its own docs.
- **Contested?** Mildly. attrs advertises that it *"doesn't force type annotations on you if you don't like them"* while also calling itself *"the best way to embrace type hints gradually"* — i.e. even the typed-class camp treats annotations as opt-in leverage, not obligation. I found no respected practitioner arguing for `--strict` on throwaway scripts.

### 14. A handed-over tool must be runnable and testable in two commands
- **Rule:** Ship a `pyproject.toml` with a `[build-system]` section, a `dev` dependency group containing `pytest`, and at least one test that invokes the tool the way the user does — so that `git clone && cd && uv run pytest` works with no further instructions.
- **Failure prevented:** The handover failure mode. The client's maintainer cannot reproduce the environment, so they never run the tests, so they never change the code — they rewrite it or abandon it. Simon Willison on adopting exactly this: *"Projects that use this pattern become a whole lot easier for other people to hack on … No need to think about virtual environments or development dependencies - this just works."* He also documents the sharp edge: without `[build-system]` (or `tool.uv.package = true`) `uv run pytest` fails with `ModuleNotFoundError` because the project is never installed into the env.
- **Source:** Simon Willison, *Dependency groups and uv run* — https://til.simonwillison.net/uv/dependency-groups ; *Using uv to develop Python command-line applications* — https://til.simonwillison.net/python/uv-cli-apps (*"using `uv run` habitually solves that for me"* — no venv activation). The end-to-end test shape is in his own cookiecutter: `CliRunner().invoke(cli, ["--version"])`, asserting `result.exit_code == 0` — https://github.com/simonw/click-app/blob/main/%7B%7Bcookiecutter.hyphenated%7D%7D/tests/test_%7B%7Bcookiecutter.underscored%7D%7D.py
- **Enforcement:** MECHANICAL as a smoke check (`uv run pytest` in a clean clone must pass in CI); JUDGMENT for what the end-to-end test asserts.
- **Contested?** No. Note the shape differs by deliverable: a single-file PEP 723 script (practice 1) has no `pyproject.toml`; the moment it grows a test file it should become a package.

### 15. Every test says, in one line, what it proves
- **Rule:** Give each test a docstring or comment stating the intent — the property being defended, not a restatement of the code.
- **Failure prevented:** A year later a test fails and nobody — including you — can tell whether the behaviour or the test is wrong, so the test gets deleted. Hynek: *"It might be obvious what property is tested under what circumstances but you have no idea why you test it"*; the asserted value is often *"a side-effect of what we're actually testing."* For handover code this is the difference between a safety net and a tripwire the client cuts.
- **Source:** Hynek Schlawack, *Why You Should Document Your Tests* — https://hynek.me/articles/document-your-tests/ (*"clear writing requires clear thinking"*; warns against *"redundant linguistic boilerplate"*).
- **Enforcement:** MECHANICAL if you want it — Hynek's own gate: `interrogate -vv --fail-under 100 --whitelist-regex "test_.*" tests`. Otherwise JUDGMENT.
- **Contested?** No disagreement found; Hynek notes the policy initially struck even him as *"baffling"*, which is honest about the adoption cost.

### 16. Property-based tests only for genuine invariants; they do not replace examples
- **Rule:** Reach for Hypothesis when the code has a round-trip or an invariant (serialise/parse, encode/decode, a diff that must be idempotent, a filter that must never widen a permission set); otherwise write example tests.
- **Failure prevented:** Two wasted-effort failures — writing contrived strategies for glue code that has no invariant, and *not* using it where a round-trip bug hides (the docs' own `nan` sorting example). Hypothesis is explicit about its scope: *"Property-based testing is a powerful addition to unit testing. It is not always a replacement."*
- **Source:** Hypothesis, *Introduction* → *When to use Hypothesis and property-based testing* — https://hypothesis.readthedocs.io/en/latest/tutorial/introduction.html (*"Look for round-trip properties: encode/decode, serialize/deserialize … These property-based tests tend to be both powerful and easy to write"*; *"Look for `@pytest.mark.parametrize` in your existing tests"*; *"Simply call your code with random inputs … You might be surprised how often this finds crashes"*).
- **Enforcement:** JUDGMENT.
- **Contested?** No — the maintainers themselves set the modest bar. For a 200-line automation script the honest answer is: usually not worth it; the exception is a parser or a permission-diff function.

### 17. Justify every dependency; prefer the stdlib
- **Rule:** Before adding a package, ask whether you are importing one function and compiling a hundred; write the small thing yourself and prefer code that will still work untouched in three years.
- **Failure prevented:** The client inherits a dependency treadmill they have no capacity to service — Dependabot noise, transitive CVEs, and a build that stops resolving. Armin: *"The goal of code in many ways should be to be written in a way that it does not need updates … when you end up using one function, but you compile hundreds, some alarm bell should go off."*
- **Source:** Armin Ronacher, *Build It Yourself* — https://lucumr.pocoo.org/2025/1/24/build-it-yourself/ (*"we should give kudos to engineers who write a small function themselves instead of hooking in a transitive web of crates. We should be suspicious of big crate graphs."*)
- **Enforcement:** JUDGMENT.
- **Contested?** **Yes, and instructively so — by the same author.** Armin also wrote Click, and Click's own rationale documents where the stdlib genuinely runs out: *"`argparse` does not allow proper nesting of commands by design and has some deficiencies when it comes to POSIX compliant argument handling"*, plus *"`argparse` has built-in behavior to guess if something is an argument or an option … the behaviour becomes unpredictable"* (https://click.palletsprojects.com/en/stable/why/). So: `argparse` for a flat script with a handful of flags (zero dependencies, any maintainer can read it); Click when you need subcommands, composability, env-var loading or file handling. Armin explicitly allows this — *"it's not black and white. There are the important libraries that solve hard problems."* Note Click deliberately restricts customisation (*"Too much customizability would break this promise"*) — that constraint is a feature for handover code.

### 18. PEP 8 is a nudge; run a formatter and spend the attention on the reading path
- **Rule:** Delegate all formatting to a tool and never argue about it; then spend the saved judgment on names, function shape and control flow — and reject cleverness (comprehension abuse, metaclasses, dynamic attribute tricks) that a non-expert maintainer cannot follow.
- **Failure prevented:** Two failures at once — bikeshedding on whitespace, and PEP 8-clean code that is still unreadable. PEP 8 disclaims its own authority: *"know when to be inconsistent – sometimes style guide recommendations just aren't applicable"*, and lists as a reason to ignore a guideline *"When applying the guideline would make the code less readable."* Hettinger's talk exists precisely to teach *"the hazards of the PEP 8 style guide"* and to *"Avoid the hazards associated with a too shallow interpretation of PEP 8."*
- **Source:** PEP 8, *A Foolish Consistency is the Hobgoblin of Little Minds* — https://peps.python.org/pep-0008/ ; Raymond Hettinger, *Beyond PEP 8 — Best practices for beautiful intelligible code*, PyCon 2015 official abstract — https://us.pycon.org/2015/schedule/presentation/416/ (*"Learn to avoid some of the hazards of the PEP 8 style guide and learn what really matters for creating beautiful intelligible code"*; *"Learn how to leverage Python's toolset for maximum effect (named tuples, keyword arguments, doctests, decorators, content managers, properties, modules, packages, logging, and exception handlers)"*), video: https://www.youtube.com/watch?v=wf-BqAjZb8M
- **Enforcement:** MECHANICAL for layout (`ruff format`, `ruff check`); PEP 8 itself notes the 79-char limit may be raised to 99 by agreement. **JUDGMENT for cleverness** — this is the anti-slop rule and cannot be linted.
- **Contested?** Yes, in emphasis. PEP 8 is prescriptive about layout; Hettinger's whole thesis is that layout compliance is nearly worthless next to API and naming quality. Both are right about different things — which is why layout should be automated away entirely.

### 19. Lint, type-check and vulnerability-audit run in CI, with tool versions pinned
- **Rule:** Put `ruff`, the type checker and `pip-audit` behind a pinned-version gate that runs in CI, not only on your laptop; a red gate blocks the merge.
- **Failure prevented:** "It passed on my machine" — different tool versions produce different verdicts, and a check that only runs locally stops running the day you hand over. mypy's own guidance: *"Make sure everyone runs mypy with the same version of mypy, for instance by pinning mypy with the rest of your dev requirements … you'll want to make sure to run mypy as part of your Continuous Integration (CI) system as soon as possible. This will prevent new type errors from being introduced."* On the supply-chain side, `pip-audit` exits `1` on any known vulnerability and *"cannot be suppressed"* — the gate is real.
- **Source:** Anthony Sottile, `pre-commit` configuration reference — hooks are addressed by `repo` + `rev` (*"the revision or tag to clone at"*), with `pre-commit autoupdate` as the deliberate, reviewable bump path, and `pre-commit run --all-files` for the full sweep: https://github.com/pre-commit/pre-commit.com/blob/main/sections/plugins.md and https://github.com/pre-commit/pre-commit.com/blob/main/sections/usage.md . mypy CI guidance: https://mypy.readthedocs.io/en/stable/existing_code.html . `pip-audit` (PyPA, maintained by Trail of Bits with Google support), including `--locked` to audit lockfiles, `--require-hashes` for repeatable audits, and an official GitHub Action: https://github.com/pypa/pip-audit
- **Enforcement:** MECHANICAL throughout — pinned `rev:` per hook; `pip-audit -r requirements.txt` or `pip-audit --locked`; `uv sync --locked` (practice 2) in the same job.
- **Contested?** One documented nuance: `pip-audit`'s own `pre-commit` example sets `ci: skip: [pip-audit]` because *"pre-commit.ci does not allow network calls"* — so the audit belongs in your CI workflow, not in the pre-commit hook set. Also note practice 3's tension: audits only help if you are actually *able* to upgrade, which is why speculative upper bounds are harmful.

## Disagreements and open questions

1. **Upper bounds on dependencies (practice 3) — the sharpest real split.** Brett Cannon and Hynek Schlawack both say: lower bound only, block specific broken releases, never speculative majors. Poetry's documented default does the opposite (`poetry add` writes `>=4.0.0,<5.0.0`). Hynek calls this out by name and tells you to undo it by hand. Consequence for the guardrail file: if Poetry is in play, its default must be explicitly overridden; on uv it is a non-issue.
2. **pydantic for domain objects (practice 12).** Hynek/attrs: pydantic is a validation library for *Commands* — untrusted input at the edge — and letting it model your domain means re-validating trusted data and letting your API shape apply design pressure to business code. The dominant FastAPI-era practice is pydantic everywhere. Unresolved in the community; for handover scripts I would follow the stdlib-`dataclasses`-plus-a-parse-boundary line because it minimises what the client must learn.
3. **PEP 8's authority (practice 18).** PEP 8 is prescriptive; Hettinger's entire talk is that shallow PEP 8 compliance is a hazard. Reconciled by automating layout and treating everything else as design.
4. **Dependency minimalism vs. good libraries (practice 17)** — held in tension by the same person (Armin Ronacher: "Build It Yourself" *and* Click). Not a contradiction, but the guardrail file should say which side of the line a given case falls on rather than pretending there is a rule.
5. **Lock-file tooling.** uv is where Hynek and Simon Willison have landed; Brett Cannon's PEP 751 (`pylock.toml`) exists precisely because uv, Poetry and PDM could not agree, and he documents Astral pushing to scale the spec back to "requirements.txt v2". If tool-independence matters for a client deliverable, `pylock.toml` / `uv export` is the hedge. Open question: PDM has adopted `pylock.toml`; uv and pip have "some form of support" (Cannon, Oct 2025) — I did not verify the current completeness of uv's `pylock.toml` support.
6. **`structlog` vs stdlib `logging` for a 200-line script.** Hynek's own dependency bar argues against pulling in `structlog` for a script; his own structured-logging argument argues for it once logs are aggregated. I found no source drawing the line, so the guardrail rule has to be conditional ("structured once a machine reads it").

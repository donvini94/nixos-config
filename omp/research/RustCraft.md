## Practices

### 1. Pick the error type by audience, not by taste
- **Rule:** In a library, define your own error type with `thiserror`; in a binary or application layer, return `anyhow::Result` and attach `.context(...)` at each step.
- **Failure prevented:** A library returning `anyhow::Error` gives callers nothing to match on, so they parse `Display` strings; an application hand-rolling enums produces dozens of variants nobody ever matches, and loses the "what was I doing" context that makes a bare `No such file or directory` undebuggable.
- **Source:** dtolnay, thiserror README, *Comparison to anyhow*: "Use thiserror if you care about designing your own dedicated error type(s) so that the caller receives exactly the information that you choose in the event of failure. This most often applies to library-like code. Use Anyhow if you don't care what error type your functions return, you just want it to be easy." https://github.com/dtolnay/thiserror — and the mirror-image statement in anyhow's README. Also: "Thiserror deliberately does not appear in your public API… switching from handwritten impls to thiserror or vice versa is not a breaking change."
- **Enforcement:** JUDGMENT
- **Contested?** Not between dtolnay and anyone credible; but note dtolnay's own framing is about *who consumes the error*, not about the crate-type. A library whose errors are never inspected legitimately uses `anyhow` internally, and thiserror's own README blesses `#[error(transparent)] Other(#[from] anyhow::Error)`.

### 2. Keep a library's error representation opaque; expose classification, not variants
- **Rule:** Make the public error type a single opaque struct wrapping a private representation, and expose inspection through a `#[non_exhaustive]` fieldless `kind()` enum plus accessors — never a public enum whose variants embed dependency error types.
- **Failure prevented:** A public `enum Error { Tokio(tokio::io::Error), Deserialize(serde_json::Error), … }` makes every dependency's major version bump *your* major version bump, and freezes layout so that boxing a fat variant later is a breaking change.
- **Source:** matklad, *Study of `std::io::Error`*: "A common anti-pattern for implementing the first case is to define a kitchen-sink enum… First, exposing errors from underlying libraries makes them a part of your public API. Major semver bump in your dependency would require you to make a new major version as well. Second, it sets all the implementation details in stone… if you notice that the size of `ConnectionDiscovery` is huge, boxing this variant would be a breaking change." https://matklad.github.io/2020/10/15/study-of-std-io-error.html — corroborated by dtolnay's documented `#[error(transparent)] pub struct PublicError(#[from] ErrorRepr)` pattern ("Private and free to change across minor version of the crate") and by *Rust for Rustaceans* ch. 4, whose sections are literally "Enumeration / Opaque Errors / Special Error Cases".
- **Enforcement:** JUDGMENT
- **Contested?** matklad goes further than most: he argues `serde_json::from_reader` should have returned `io::Error` rather than carrying an `Io` variant, and flags this as his own opinion ("I'd be delighted to be proven wrong"). The kitchen-sink enum is still what most crates ship.

### 3. Every `unsafe` block carries a `// SAFETY:` comment; every `unsafe fn` carries a `# Safety` doc section
- **Rule:** Precede every `unsafe` block and `unsafe impl` with a `// SAFETY:` comment naming the invariant that discharges the obligation, and document every `unsafe fn` with a `# Safety` section stating what the caller must uphold.
- **Failure prevented:** Unsound code that nobody can review. The std policy is explicit that writing the justification is itself the bug-finding step.
- **Source:** std-dev-guide, *Safety comments*: "each `unsafe` block should have a `SAFETY:` comment explaining why the block is safe, which invariants are used and must be respected." https://github.com/rust-lang/std-dev-guide/blob/master/src/policy/safety-comments.md — and clippy's own lint text: "Undocumented unsafe blocks and impls can make it difficult to read and maintain code. Writing out the safety justification may help in discovering unsoundness or bugs." (`clippy_lints/src/undocumented_unsafe_blocks.rs`). The `# Safety` half is ratified as API guideline C-FAILURE: "Unsafe functions should be documented with a \"Safety\" section that explains all invariants that the caller is responsible for upholding."
- **Enforcement:** MECHANICAL — `clippy::undocumented_unsafe_blocks` (category `restriction`, allow-by-default; must be opted into) and `clippy::missing_safety_doc` (category `style`, **warn** by default, so already on).
- **Contested?** Yes, and this is worth knowing. The `// SAFETY:` *block* convention is std/clippy discipline, not universal practice among top crate authors. Gjengset's `left-right` documents `/// # Safety` on its `unsafe fn`s (`aliasing.rs`, `write.rs`) but contains **zero** `// SAFETY:` comments across all eight source files, despite being a lock-free primitive full of raw pointers. Clippy itself declines to make the lint default (`restriction`). So: `missing_safety_doc` is consensus; `undocumented_unsafe_blocks` is a house rule you must choose.

### 4. Deny `unsafe_op_in_unsafe_fn`; one unsafe operation per block
- **Rule:** Set `#![deny(unsafe_op_in_unsafe_fn)]` and wrap each individual unsafe operation in its own `unsafe { }` block with its own justification.
- **Failure prevented:** In an `unsafe fn` without this lint, the whole body is an implicit unsafe block, so accidentally calling `offset` instead of `wrapping_offset` compiles silently. One big block per function also means a single comment purporting to justify several independent obligations.
- **Source:** Ralf Jung, RFC 2585: "`unsafe {}` blocks are about *discharging* obligations, but `unsafe fn` are about *defining* obligations. The fact that the body of an `unsafe fn` is also implicitly treated like a block has made it hard to realize this duality even for experienced Rust developers." https://rust-lang.github.io/rfcs/2585-unsafe-block-in-unsafe-fn.html — now warn-by-default in edition 2024 (https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-op-in-unsafe-fn.html). The per-operation rule is clippy's: "Combined with `undocumented_unsafe_blocks`, this lint ensures that each unsafe operation must be independently justified."
- **Enforcement:** MECHANICAL — `rustc` lint `unsafe_op_in_unsafe_fn` (warn by default in edition 2024; explicitly `deny`d at crate root by tokio, syn and anyhow) + `clippy::multiple_unsafe_ops_per_block` (`restriction`, opt-in).

### 5. If the crate has `unsafe` or atomics, Miri and Loom run in CI
- **Rule:** Any crate containing `unsafe` runs `cargo miri test` in CI; any crate implementing a concurrency primitive additionally ships a `--cfg loom` test target.
- **Failure prevented:** UB and memory-ordering bugs that pass every normal test on x86 (which is strongly ordered) and then break on ARM or under a different optimiser.
- **Source:** Gjengset's own reference CI, `safety.yml`: "This workflow runs checks for unsafe code… miri - detects undefined behavior and memory leaks; address sanitizer; leak sanitizer; loom - Permutation testing for concurrent code", with `cargo miri test` and `cargo test --release --test loom` under `LOOM_MAX_PREEMPTIONS: 2`. https://github.com/jonhoo/rust-ci-conf/blob/main/.github/workflows/safety.yml — he applies it to himself: `left-right` has `tests/loom.rs` and the same `safety.yml`. *Rust for Rustaceans* ch. 10 names the sections "Write Stress Tests" and "Use Concurrency Testing Tools".
- **Enforcement:** MECHANICAL — CI job.

### 6. `#![forbid(unsafe_code)]` is a statement of fact, not a security claim
- **Rule:** Add `#![forbid(unsafe_code)]` only after the crate genuinely contains no `unsafe`, and never present its presence or an unsafe-block count as evidence that code is secure.
- **Failure prevented:** Two opposite errors: (a) reaching for `unsafe` in application code that never needed it, and (b) treating "0 unsafe blocks" as an audit result, which it is not — and conversely rejecting a correct, audited primitive because it uses `unsafe`.
- **Source:** rust-secure-code WG, safety-dance, step 5: "If you have completely cleansed a crate of `unsafe`, add a `#![forbid(unsafe_code)]` attribute to its `src/lib.rs` or `main.rs`." https://github.com/rust-secure-code/safety-dance — against which cargo-geiger's README states: "This tool is not meant to advise directly whether the code ultimately is truly insecure or not… The use of unsafe is nuanced and necessary in some cases and any motivation to use it is outside the scope of cargo-geiger," linking Gjengset's *Demystifying unsafe code* talk and "The Stigma around Unsafe". https://github.com/geiger-rs/cargo-geiger
- **Enforcement:** MECHANICAL for the attribute (`rustc` lint `unsafe_code`); JUDGMENT for whether it is honest and whether it means anything.
- **Contested?** Yes — see "Disagreements" below. safety-dance is the "drive it to zero" camp; cargo-geiger (the tool safety-dance itself recommends) is on record that the number is input to an audit, not a verdict. Note also the Rustonomicon's list of things Rust considers *safe*: "Deadlock… Leak memory… Overflow integers… Delete the production database" — the absence of `unsafe` bounds a specific class of bug and nothing else.

### 7. Set the crate-root warn block on day one
- **Rule:** Put `#![warn(missing_docs, missing_debug_implementations, unreachable_pub, rust_2018_idioms)]` at the crate root of every library.
- **Failure prevented:** Undocumented public API that ossifies before anyone writes docs; types that cannot be printed in a panic message or a log line because they lack `Debug`; items that are `pub` inside private modules and become part of your API by accident.
- **Source:** This exact set is what the practitioners actually run. tokio, `tokio/src/lib.rs` lines 7–13: `#![warn(missing_debug_implementations, missing_docs, rust_2018_idioms, unreachable_pub)]` / `#![deny(unused_must_use, unsafe_op_in_unsafe_fn)]`. Gjengset, `left-right/src/lib.rs` lines 170–176: `#![warn(missing_docs, rust_2018_idioms, missing_debug_implementations, broken_intra_doc_links)]`. rust-analyzer's `[workspace.lints.rust]` sets `unreachable_pub = "warn"`, `unused_lifetimes = "warn"`, `elided_lifetimes_in_paths = "warn"`. The `Debug` requirement is ratified as C-DEBUG ("All public types implement `Debug`").
- **Enforcement:** MECHANICAL — rustc lints.

### 8. `unused_must_use` is denied; `#[must_use]` is added only where ignoring the value is almost certainly a bug
- **Rule:** `#![deny(unused_must_use)]` at the crate root; add `#[must_use]` to a type or function only when discarding its output is almost certainly a mistake, and not merely because it returns something.
- **Failure prevented:** Silently dropped `Result`s and silently discarded lazy iterator chains; and, on the other side, nuisance warnings that train people to write `let _ =` reflexively — which then hides a real dropped `Result`.
- **Source:** std-dev-guide, *When to add `#[must_use]`*: "The `#[must_use]` attribute can be applied to types or functions when failing to explicitly consider them or their output is almost certainly a bug… On the other hand, `thread::JoinHandle` isn't `#[must_use]` because spawning fire-and-forget work is a legitimate pattern and forcing callers to explicitly ignore handles could be a nuisance rather than an indication of a bug." https://github.com/rust-lang/std-dev-guide/blob/master/src/policy/must-use.md — tokio denies `unused_must_use` at the crate root.
- **Enforcement:** MECHANICAL for `unused_must_use` (rustc, warn by default); JUDGMENT for placement.
- **Contested?** Yes. clippy ships `must_use_candidate` (`pedantic`) to suggest blanket annotation, and its own docs concede "Not bad at all… Expect many false positives." dtolnay explicitly allows both `clippy::must_use_candidate` and `clippy::return_self_not_must_use` in `anyhow/src/lib.rs` and `syn/src/lib.rs`. The std policy and dtolnay are aligned *against* the pedantic lint here.

### 9. Future-proof public data: private fields, `#[non_exhaustive]`, no derivable bounds
- **Rule:** Public structs have private fields with accessors; enums and config structs you expect to grow are `#[non_exhaustive]`; and never write trait bounds on a data structure that `derive` already provides.
- **Failure prevented:** All three are the same failure: an additive change becomes a major version. Adding a variant breaks every exhaustive `match`; adding a field breaks every struct literal; and `struct Bad<T: Clone + Debug + PartialEq>` means that later deriving `PartialOrd` forces a bound onto every downstream user.
- **Source:** RFC 2008: "Adding this hint to enums will force downstream crates to add a wildcard arm to `match` statements, ensuring that adding new variants is not a breaking change… Adding this new setting is now a breaking change!" https://rust-lang.github.io/rfcs/2008-non-exhaustive.html — API guidelines C-STRUCT-PRIVATE ("Making a field public is a strong commitment: it pins down a representation choice, and prevents the type from providing any validation or maintaining any invariants") and C-STRUCT-BOUNDS, which lists the traits that must *never* appear in bounds: `Clone`, `PartialEq`, `PartialOrd`, `Debug`, `Display`, `Default`, `Error`, `Serialize`, `Deserialize`, `DeserializeOwned`. https://rust-lang.github.io/api-guidelines/future-proofing.html
- **Enforcement:** JUDGMENT (`cargo-semver-checks` catches the breakage *after* you commit it, not the design decision).

### 10. Seal traits that are not meant to be implemented downstream
- **Rule:** If a public trait exists only so *your* types can implement it, give it a private `Sealed` supertrait and say so in the rustdoc.
- **Failure prevented:** Without sealing, adding a method to a public trait is a breaking change forever; with sealing, it is a patch release.
- **Source:** API guidelines C-SEALED: "The empty private `Sealed` supertrait cannot be named by downstream crates, so we are guaranteed that implementations of `Sealed` (and therefore `TheTrait`) only exist in the current crate. We are free to add methods to `TheTrait` in a non-breaking release… To avoid frustrated users trying to implement the trait, it should be documented in rustdoc that the trait is sealed." https://rust-lang.github.io/api-guidelines/future-proofing.html — cited examples are `serde_json::value::Index` and `byteorder::ByteOrder`.
- **Enforcement:** JUDGMENT

### 11. Arguments carry meaning in their types, not in their position
- **Rule:** Never accept a bare `bool`, bare numeric or bare `String` for a domain concept; introduce a newtype or a small enum, and prefer a builder over a constructor with five same-typed parameters.
- **Failure prevented:** Unit and argument-order confusion that the compiler cannot see. The API guidelines cite the Mars Climate Orbiter for the `Miles`/`Kilometers` case; `Widget::new(true, false)` is unreviewable at the call site.
- **Source:** API guidelines C-NEWTYPE and C-CUSTOM-TYPE: "Core types like `bool`, `u8` and `Option` have many possible interpretations. Use a deliberate type (whether enum, struct, or tuple) to convey interpretation and invariants." https://rust-lang.github.io/api-guidelines/type-safety.html — Amos Wenger reaches the same conclusion by contrast with Go, and, importantly, prices it: "once you *have* experienced 'good design', it's really hard to go back… Even after acknowledging that 'good design' inevitably comes at a cost, whether it's cognitive load, compile times, making hiring more challenging." https://fasterthanli.me/articles/abstracting-away-correctness — the typestate extension (state encoded in the type, transitions consuming `self`) is documented officially by the Embedded WG: https://docs.rust-embedded.org/book/static-guarantees/typestate-programming.html
- **Enforcement:** JUDGMENT (`clippy::fn_params_excessive_bools` and `struct_excessive_bools` catch only the crudest cases — and dtolnay allows both in `syn`).

### 12. Decide generic-vs-`dyn` once, at the trait definition, and default to less abstraction
- **Rule:** Before writing a trait, decide whether it will be used as a bound or as a trait object, and do not introduce a trait at all until there is a second implementor.
- **Failure prevented:** The API guidelines list the costs in the guidelines themselves: "*Code size*. Specializing generic functions means that the function body is duplicated" and "*Signature verbosity*. Heavy use of generics can make it more difficult to read and understand a function's signature" — versus, for `dyn`, "*No generic methods*… *Dynamic dispatch and fat pointers*." Retrofitting object-safety onto a trait with generic methods is a rewrite.
- **Source:** API guidelines C-GENERIC / C-OBJECT: "When designing a trait, decide early on whether the trait will be used as an object or as a bound on generics." https://rust-lang.github.io/api-guidelines/flexibility.html — *Rust for Rustaceans* ch. 3 organises exactly this way ("Generic Arguments", "Object Safety", "Borrowed vs. Owned", then "Constrained: Type Modifications / Trait Implementations / Hidden Contracts"). dtolnay's *case-studies* README is the cleanest statement of the anti-over-abstraction position: "the difference between someone who is competent with macros vs an expert at macros mostly has nothing to do with how good they are 'at macros'… learning more 'about macros' won't change that; but learning more about every other part of Rust will." https://github.com/dtolnay/case-studies — and ch. 7 of *Rust for Rustaceans* has a section literally titled "So You Think You Want a Macro" alongside "The Cost of Procedural Macros".
- **Enforcement:** JUDGMENT
- **Contested?** There is a real tension inside the API Guidelines themselves: C-GENERIC says "Functions minimize assumptions about parameters by using generics" and prefers `fn foo<I: IntoIterator<Item = i64>>(iter: I)` over `fn foo(c: &[i64])`, while the same page enumerates monomorphisation bloat and signature verbosity as the price. matklad's `std::io::Error` study points the other way with a concrete technique: "Generic `new` function delegates to monomorphic `_new` function. This improves compile time, as less code needs to be duplicated during monomorphization."

### 13. Never hold an async task away from an `.await`
- **Rule:** In async code, never spend more than roughly 10–100 microseconds between `.await` points: move synchronous I/O to `tokio::task::spawn_blocking`, CPU-bound work to `rayon` (bridged with a `oneshot`), and never-ending loops to a dedicated `std::thread`.
- **Failure prevented:** Cooperative-scheduling starvation that is invisible in local testing. Ryhl names exactly why: the multi-threaded runtime spawns one thread per core, "This is enough that you can miss the issue when testing locally, but sufficiently few that you will very quickly run out of threads when running the code for real." A blocking loop on `spawn_blocking` "essentially takes away a thread from the pool permanently. Once you've done that a few times, you have no more threads in the thread pool and all other blocking tasks fail to get executed."
- **Source:** Alice Ryhl, *Async: What is blocking?*: "If you remember only one thing from this article, this should be it: Async code should never spend a long time without reaching an `.await`." and "a good rule of thumb is no more than 10 to 100 microseconds between each `.await`." https://ryhl.io/blog/async-what-is-blocking/
- **Enforcement:** JUDGMENT (no lint measures time between await points; `tokio::task::block_in_place` and the runtime's own task-dump/`--cfg tokio_unstable` metrics help after the fact).

### 14. Actors: split handle from task, spawn outside the impl, bound every channel
- **Rule:** Model long-lived owned state as an actor with two types — a `Handle` holding an `mpsc::Sender` and a task owning the state — spawn the task from the handle's constructor rather than from a `&mut self` method, and always use a bounded channel.
- **Failure prevented:** Two concrete failures Ryhl names: `tokio::spawn` requires `'static`, so spawning from `&mut self` cannot give away ownership; and merging actor and handle into one struct means "you are (at least from the compiler's perspective) giving every handle access to the fields owned by the actor's task." Unbounded channels give unbounded memory growth with no backpressure.
- **Source:** Alice Ryhl, *Actors with Tokio*: "An actor is split into two parts: the task and the handle… You should still make sure to use a bounded channel so that the number of messages waiting in the channel don't grow without bound." https://ryhl.io/blog/actors-with-tokio/ — *Rust for Rustaceans* ch. 10 lists "Actors" as one of three concurrency models alongside shared memory and worker pools.
- **Enforcement:** JUDGMENT

### 15. Measure before optimising; an `#[inline(always)]` needs a benchmark attached
- **Rule:** Do not optimise code you have not profiled; prefer algorithm and data-structure changes to micro-optimisation; use `criterion` or `divan` rather than ad-hoc `Instant::now()` timing; and never add `#[inline(always)]` without a microbenchmark that justifies it.
- **Failure prevented:** Complexity bought for nothing. Nethercote states the cost directly: "Optimized code is often more complex and takes more effort to write than unoptimized code. For this reason, it is only worth optimizing hot code." Ad-hoc timing also silently reports noise as a win — criterion exists because wall-time "can suffer from high variance. In particular, tiny changes in memory layout can cause significant but ephemeral performance fluctuations."
- **Source:** Nethercote, *The Rust Performance Book*, General Tips: "The biggest performance improvements often come from changes to algorithms or data structures, rather than low-level optimizations," and Benchmarking: "Rust's built-in benchmark tests… use unstable features… Criterion and Divan are more sophisticated alternatives." https://nnethercote.github.io/perf-book/general-tips.html — std-dev-guide, *When to `#[inline]`*: "You should just about never need `#[inline(always)]`… A micro benchmark should justify the attribute." https://github.com/rust-lang/std-dev-guide/blob/master/src/policy/inline.md — criterion's documented statistics (Tukey outlier fences, bootstrapped linear regression, configurable noise threshold) are the reason to prefer it: https://bheisler.github.io/criterion.rs/book/analysis.html
- **Enforcement:** JUDGMENT for the discipline; MECHANICAL for the tooling (`cargo bench` with criterion/divan; `cargo flamegraph`/`samply`/`perf`).
- **Contested?** Nethercote softens the purist line himself: "do not stress too much about having a perfect benchmarking setup… Mediocre benchmarking is far better than no benchmarking."

### 16. Test-suite topology is a compile-time decision: one integration binary, and `mod tests;` in its own file
- **Rule:** Use at most one integration-test crate (`tests/it/main.rs`) with submodules rather than many files in `tests/`, and write `#[cfg(test)] mod tests;` pointing at a separate `tests.rs` file rather than an inline `mod tests { … }`.
- **Failure prevented:** Measured, not theoretical: cargo relinks the library once per file in `tests/`, and runs test *binaries* sequentially even though tests within a binary run in parallel. matklad reports "The time to compile the test suite decreased 3x. The size of on-disk artifacts decreased 5x" for cargo itself, and "consolidating several integration tests into one reduced the time to run the test suite from 20 seconds to just 13." The inline-vs-file point is a real incremental-rebuild win: "when you modify just the tests, Cargo is smart to not recompile the library crate."
- **Source:** matklad, *Delete Cargo Integration Tests*. https://matklad.github.io/2021/02/27/delete-cargo-integration-tests.html
- **Enforcement:** JUDGMENT (a convention; no linter checks test-crate topology).
- **Contested?** Strongly — see "Disagreements". matklad's further advice ("For a library with a public API which is published to crates.io, I avoid unit tests"; "For an internal library, I avoid integration tests all together"; "documentation tests are extremely slow… add `[lib] doctest = false`") directly opposes API guideline C-EXAMPLE.

### 17. Property-test the invariant, then promote every shrunk counterexample to a named unit test
- **Rule:** For parsers, codecs, serialisers and anything with a round-trip or ordering invariant, write property tests; commit the `proptest-regressions` directory; and copy each minimised failure into an ordinary `#[test]` with a name.
- **Failure prevented:** Exactly the class of bug hand-written cases miss. The proptest book's own worked example ships a date parser that passes five hand-written assertions and then panics on `"aAௗ0㌀0"` because it sliced a `&str` mid-character. Without promotion to a unit test, the fix is unprotected once the random seed moves on.
- **Source:** the proptest book, *Getting Started*: "If we look at the top directory after the test fails, we'll see a new `proptest-regressions` directory… The first thing we should do is add these to source control… The next thing we should do is copy the failing case to a traditional unit test since it has exposed a bug not similar to what we've tested in the past." https://proptest-rs.github.io/proptest/proptest/getting-started.html — *Rust for Rustaceans* ch. 6 treats this as first-class, with sections "Test Generation" and "Test Augmentation" (i.e. `proptest`/`quickcheck` and mutation/fault injection) beside "The Test Harness", "`#[cfg(test)]`", "Doctests" and "Performance Testing".
- **Enforcement:** JUDGMENT

### 18. The CI matrix is part of the design, not an afterthought
- **Rule:** Every library runs, on every PR: `cargo fmt --check`; clippy on **stable and beta**; `cargo docs-rs` on nightly; `cargo hack --feature-powerset check`; a pinned-MSRV `cargo check`; and `cargo-semver-checks`.
- **Failure prevented:** Each job maps to a specific real failure. Beta clippy gives "early warning of new lints which are regularly introduced in beta channels" so upgrades are never a wall of errors. `cargo hack --feature-powerset` catches non-additive features — "to ensure that features are all additive which is required for feature unification" — the classic "compiles alone, breaks when a sibling crate enables one more feature" bug. MSRV drift and accidental semver breakage are otherwise found by users.
- **Source:** Gjengset, `rust-ci-conf/.github/workflows/check.yml` (its header comment enumerates exactly: `fmt`, `clippy`, `doc`, `hack`, `msrv`; the workflow also runs `obi1kenobi/cargo-semver-checks-action`). https://github.com/jonhoo/rust-ci-conf/blob/main/.github/workflows/check.yml — corroborated by *Rust for Rustaceans* ch. 5, whose sections are "Minimum Supported Rust Version", "Minimal Dependency Versions", "Changelogs", "Unreleased Versions".
- **Enforcement:** MECHANICAL

### 19. Flat workspace, `crates/*`, directory name equals crate name, automation in an `xtask` crate
- **Rule:** Lay a multi-crate project out flat under `crates/` with a virtual manifest at the root, name every directory exactly like its crate, use `version = "0.0.0"` for unpublished internal crates, and put all repo automation in a Rust `xtask` crate rather than shell scripts.
- **Failure prevented:** Hierarchical layouts rot: "there are no perfect hierarchies. With a flat structure, adding or splitting the crates is trivial. With a tree, you need to figure out where to put the new crate, and, if there isn't a perfect match for it already, you'll have to either: add a stupid mostly empty folder near the top; add a catch-all utils folder; place the code in a known suboptimal directory." Also: Cargo's crate namespace is flat, so a directory tree creates a second, divergent hierarchy.
- **Source:** matklad, *Large Rust Workspaces* — the rust-analyzer layout (32 crates under `crates/`) is the worked example, with the explicit threshold "for projects in between ten thousand and one million lines of code, the flat layout makes the most sense." https://matklad.github.io/2021/08/22/large-rust-workspaces.html
- **Enforcement:** JUDGMENT
- **Contested?** The related `mod.rs`-vs-`foo.rs` question has **no** consensus, and clippy says so structurally: it ships *two mutually exclusive* `restriction` lints, `mod_module_files` ("bans `mod.rs` files") and `self_named_module_files` ("requires `mod.rs` files"), both allow-by-default. Justification given for either is identical and content-free: "Having multiple module layout styles in a project can be confusing." Pick one for consistency; there is no failure mode behind the choice itself.

## Disagreements and open questions

**1. Doctests and unit tests: matklad vs. the API Guidelines (and Gjengset).** The API Guidelines make doctests near-mandatory — C-EXAMPLE: "Every public module, trait, struct, enum, function, method, macro, and type definition should have an example that exercises the functionality," with C-QUESTION-MARK insisting examples use `?` and never `unwrap` because "example code is often copied verbatim by users." *Rust for Rustaceans* gives Doctests their own section in ch. 6. matklad argues the opposite from build-time evidence: "documentation tests are extremely slow. Each doc test is linked as a separate binary. For this reason, avoid doc tests in internal libraries for big projects and add this to `Cargo.toml`: `[lib] doctest = false`," and "For a library with a public API which is published to crates.io, I avoid unit tests" in favour of a single `tests/it` crate that is forced through the real public API. Both sides are right about different things: doctests are documentation that cannot rot, and they are the slowest test kind in Rust. The resolution I would encode: doctests are mandatory on published API surface, forbidden on internal crates.

**2. Clippy `pedantic`: dtolnay runs it and fights it; matklad's rust-analyzer does not run it at all.** dtolnay's CI runs `cargo clippy --all-features --tests --benches -- -Dclippy::all -Dclippy::pedantic` (`syn/.github/workflows/ci.yml` line 183) — and then `syn/src/lib.rs` carries an `#![allow(...)]` list of ~55 clippy lints, several annotated with the clippy bug they are working around: `clippy::let_underscore_untyped, // https://github.com/rust-lang/rust-clippy/issues/10410`, `clippy::match_wildcard_for_single_variants, // clippy bug: rust-clippy#6984`, `clippy::unconditional_recursion, // rust-clippy#12133`. `anyhow/src/lib.rs` lines 213–236 allow a similar set including `missing_errors_doc`, `missing_panics_doc`, `module_name_repetitions`, `must_use_candidate`, `uninlined_format_args`, `wildcard_imports`. rust-analyzer takes the other route entirely: its `[workspace.lints.clippy]` enables only `complexity`/`correctness`/`perf`/`style`/`suspicious`, sets `restriction = "allow"`, and never mentions `pedantic` or `nursery`; it *adds* `dbg_macro`, `todo`, `print_stdout`, `print_stderr` as warns ("CI raises these to deny"), and allows a documented list including `useless_asref` ("Has a bunch of false positives"), `assigning_clones` ("Has false positives"), `vec_init_then_push` ("Does not work with macros"), `unnecessary_map_or` ("triggers on cases where its invalid to do so due to it ignoring move analysis"). tokio is a third data point closer to rust-analyzer: no `pedantic`, four targeted allows (`cognitive_complexity`, `large_enum_variant`, `module_inception`, `needless_doctest_main`). **Named places practitioners say clippy is wrong**, with receipts: `must_use_candidate` (clippy's own docs: "Expect many false positives"), `missing_errors_doc`/`missing_panics_doc`, `module_name_repetitions`, `uninlined_format_args`, `wildcard_imports`, `needless_lifetimes`, `similar_names`, `too_many_arguments`, `type_complexity`. Nobody in this survey enables `nursery` or `restriction` wholesale.

**3. The `// SAFETY:` block convention is policy in std and merely a house rule elsewhere.** std-dev-guide makes it binding for the standard library; clippy files the enforcing lint under `restriction` (allow-by-default); and Gjengset's `left-right` — a lock-free primitive with `unsafe impl Send`/`Sync`, `NonNull`, `drop_in_place` and manual aliasing — has zero `// SAFETY:` comments while carefully documenting `/// # Safety` on its `unsafe fn`s. So there is a genuine split between "document the obligation you define" (universal) and "document the obligation you discharge" (std, not universal).

**4. `unsafe` as a metric.** safety-dance's process ends in "add `#![forbid(unsafe_code)]`… help others discover Safety Dance by adding a badge." cargo-geiger — the tool safety-dance itself recommends for finding the unsafe — opens its *Intended Use* section with "This tool is not meant to advise directly whether the code ultimately is truly insecure or not" and links both the "stigma around unsafe" discussion and Gjengset's *Demystifying unsafe code*. safety-dance is also honest that eliminating unsafe is not free and not always possible: "benchmarks *must* actually be used to back up any performance loss claims."

**Open question I did not resolve:** whether `anyhow` is acceptable *inside* a library. dtolnay's thiserror README explicitly supports `#[error(transparent)] Other(#[from] anyhow::Error)` as an "anything else" variant, which is in tension with the crisp "anyhow is for applications" framing everyone quotes. I found no statement from him adjudicating it.

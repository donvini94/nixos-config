#+title: AI stack: requirements for customer deployments

Source: requirements interviews with the operator, 2026-10. This is the reference for
turning =ai/= into a standalone flake. Statements marked /Gap/ are required but not
yet implemented in this repository.

* Product and customers

- Small German Mittelstand companies and small businesses. Customers are non-technical
  and buy outcomes (automations, agent tasks, messaging assistants); they do not know
  n8n or Hermes exist. The operator runs all IT.
- One dedicated single-tenant Hetzner Cloud x86 VPS per customer (4-8 vCPU, 16-32 GB,
  no GPU), rented and billed by the operator. The customer never logs in to the server;
  customer staff only use the public web applications (Paperless, Onyx, n8n forms).
- EU/German hosting for servers and backups. LLM calls go through Requesty only, with
  EU-compliant models and a signed DPA/AVV.

* Flake

- Name =ai-stack=. It starts as a subflake in =ai/= (=ai/flake.nix=, outputs
  =nixosModules=, =packages=, =checks=), consumed by this repository through a path
  input. It moves to a private GitHub repository when the operator says so and is then
  consumed as a =github:= input.

* Components

Always installed:
- n8n with task runners on PostgreSQL (host =services.postgresql=, dedicated role, local
  socket). Alucard migrates its SQLite database (n8n export/import, same encryption key).
  /Gap/
- Hermes agent
- Requesty access with one key per customer
- Reverse proxy and TLS (nginx, ACME) on the customer's own domain /Gap: Alucard has this
  in hosts/alucard/services/reverse-proxy.nix/
- Intrusion protection /Gap: lives in hosts/alucard/security.nix/
- Backups /Gap: lives in hosts/alucard/backups.nix/
- Container and host vulnerability scanning (done: =ai/nixos/vulnerability-scan/=)
- Keeping images and packages updated (see Updates)
- Monitoring exporters (done: =ai/nixos/observability/exporters.nix=)
- Egress controls and Hermes isolation (see Network exposure) /Gap/
- =ai-stack.target= as a grouping unit that starts at boot (n8n, runners, Hermes). The
  polkit rules, operator group and =ai-stack-start|stop|health= are dropped; health is
  covered by =ai-stack-check=.

Optional modules at launch: Paperless-ngx and Onyx. /Gap: not implemented./
- Presets set defaults; feature flags override them, e.g. =tier = "plus"= and
  =features.onyx.enable = true=. Giving a customer a module is a one-line change.
- =basic=: the always-installed stack. =plus=: =basic= plus Paperless.
- Onyx is a separate add-on in every tier (OpenSearch makes it heavy).
- Onyx ships as Nix-managed upstream Compose: pinned compose file and image digests,
  =.env= rendered from options and sops, a systemd unit running =docker compose=,
  Renovate bumping the digests, upgrades following upstream's procedure.
- Alucard consumes both modules. Its Paperless keeps its data directory and database;
  its Onyx has no content and is replaced by the module without a backup.

Operator-only, never customer-facing: Dracula-style local inference, transcription, OMP
and Pi are personal tools and are not part of the stack.

* Separation from the operator's personal setup

Nothing in the stack may reference the operator's personal accounts, notes tree, hosts or
paths. Personal configuration stays in =hosts/= and =coding-agents/=.

* Accounts

- Each service runs as its own system user and owns its secrets; the stack has no
  notion of a human user.
- Customer hosts have no human accounts: root SSH with the operator's keys
  (=operator.sshKeys=), tailnet only, password authentication off. This lives in a
  customer-host profile that Alucard does not import.

* Network exposure

- Public (customer domain), path-allow-listed:
  - n8n: =/webhook/= (including hosted chat), =/webhook-waiting/=, =/form/=,
    =/form-waiting/= and the static assets forms need. Everything else returns 404,
    including the editor, =/rest/=, test endpoints, =/metrics= and =/healthz=.
  - Paperless and Onyx on their own subdomains with the applications' own logins, for
    customer staff.
- Hermes has no public surface. Dashboard and API stay on the tailnet; customers chat
  through messaging gateways (outbound connections) or an n8n hosted chat that calls
  Hermes.
- Everything else (SSH, Grafana, Prometheus, n8n and Hermes admin UIs, exporters) is
  reachable only over the operator's tailnet. No Tailscale Funnel.
- Tailnet access rules, kept in the fleet repository as the source of truth: customer
  hosts are =tag:customer= and initiate nothing on the tailnet; Alucard
  (=tag:monitoring=) reaches customer exporter ports only; the operator reaches SSH and
  admin UIs. A compromised customer host cannot reach Alucard, the operator's machines
  or other customers. /Gap/
- DNS: the customer's IT or registrar sets A/AAAA records the operator supplies; ACME
  uses HTTP-01, so port 80 stays open. No DNS credentials in sops.
- Edge protection on every public vhost, as on Alucard: CrowdSec with firewall bouncer,
  ModSecurity with OWASP CRS, security headers. Rate limits per path: looser on
  =/webhook/= (Meta and Telegram burst from few addresses), tighter on forms and logins.
  Per-application WAF exemptions live in the application modules.
- Egress is open to the public internet: agents search, shop, mail, call arbitrary APIs
  and post to social media, so a domain allow-list would block the product and still
  not stop exfiltration through allowed sites. Blocked: private and CGNAT ranges
  (including the tailnet), the cloud metadata endpoint and outbound port 25 (mail goes
  through the customer's provider on 587/465). Outbound connections are counted per
  destination and exported as metrics; anomalies alert.
- Hermes runs on its own container network, not the host network. It reaches only n8n's
  webhook/API endpoint, not loopback services (PostgreSQL, admin UIs) or the tailnet.
  This applies on Alucard too.
- Containment comes from credentials and approval, not the network: per-task API keys
  with spending limits, a dedicated mailbox or alias per agent, Requesty budgets. Orders,
  payments, outbound mail to new recipients, public posts and other irreversible
  actions require human approval (n8n approval steps, Hermes approvals); this is a rule
  for =ai-library= content.
- "LLM calls go through Requesty only" is enforced by configuration (no other LLM keys
  in the stack) and checked by =ai-stack-check=, not by the firewall.

* Provisioning and operation

- One private fleet repository holds one small file per customer that imports the AI
  flake. Bootstrap with nixos-anywhere and disko; the flake ships a standard Hetzner
  disk layout /Gap/. Deploy from the operator's Mac with deploy-rs as root over the
  tailnet; magic rollback guards against losing access. /Gap/
- Secrets: sops-nix in the fleet repo, one age key per customer host plus the operator
  key. Every secret change is a deploy.
- First run: =ai-stack-check= on the host reports each item as ok, missing or manual,
  and the same checks export textfile metrics, so central Grafana shows each customer's
  onboarding state and alerts on regressions. Items: DNS records point at the host,
  certificates issued, Requesty key valid, WhatsApp/Meta and Telegram set up, n8n owner
  and Hermes accounts exist, tailnet joined, backup repository initialized with a
  snapshot, Storage Box snapshots enabled (manual), with Onyx: admin account, sources,
  LLM key. /Gap/
- Workflows and agent configuration: n8n workflows, Hermes skills and a managed Hermes
  config fragment live in a private =ai-library= flake (reusable items, released by tag
  like =ai-stack=); each customer file in the fleet repository selects library items
  and adds its own from =customers/<name>/=. Credentials are never in Git; workflows
  reference them by ID, created once per customer. /Gap/
- Git wins for managed items: every deploy re-imports managed workflows (stable IDs,
  upsert, activated) and skills, overwriting UI edits. A timer compares live state with
  Git and exports a drift metric with an alert, so edits are noticed before a deploy
  replaces them. Items created only in the UI are left alone. /Gap/

* Agent operating guide

Future customer setups are performed by agents. The flake ships a lean guide:
=AGENTS.md= with the rules and =OPERATIONS.org= with procedures (onboard a customer,
deploy and promote a release, rotate a secret, restore, add or remove a module,
offboard). The fleet repository's =AGENTS.md= adds fleet specifics and points to them.
This file keeps the reasons; the guide keeps the steps. Each procedure is written when
its implementation lands and is verified on the test customer. The extraction is done
when a fresh agent session onboards the test customer from the guide alone. /Gap/

* Backups

- restic per host to a Hetzner Storage Box in Germany: one sub-account per customer,
  restricted to its directory, reached over SFTP with an SSH key in sops. The host
  prunes its own repository. Automatic Storage Box snapshots, configured once per box
  outside Nix, protect against a compromised host deleting its history.
- Encryption key in sops plus an offline copy; restore tests. /Gap/

* Updates

- Controlled, staged: Renovate bumps flake inputs and image digests, the operator
  reviews, deployment is by the operator; hosts do not update themselves.
- Alucard is the canary: it imports the stack the way a customer would and follows
  =ai-stack= main. After a soak on Alucard the operator tags a release
  (e.g. =v2026.10.1=); Renovate in the fleet repository proposes tag bumps, which the
  operator merges and deploys. /Gap/

* Monitoring and alerting

- Customer hosts run exporters only (node, cAdvisor, scan metrics through the textfile
  directory) and expose them on the tailnet interface.
- One central Prometheus, Grafana and Alertmanager on Alucard scrapes all customer hosts
  over the tailnet (=services.observability.server.hosts=).
- Alerts go to a Telegram chat through Alertmanager (e-mail optional). Implemented;
  needs a bot token (sops) and a chat id on Alucard, which do not exist yet. Tracked
  as an operator action and an =ai-stack-check= item on Alucard.
- /Gap:/ n8n metrics are only reachable on a host's loopback and are therefore scraped
  for Alucard only.

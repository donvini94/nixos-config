#+title: Handoff: extract the AI stack into a standalone flake

Delete this file when the extraction is finished.

* Goal

Turn =ai/= of this repository into a standalone NixOS flake that a private fleet
repository imports to run a small German business's AI infrastructure on a fresh
Hetzner VPS: n8n, Hermes, Requesty access, monitoring exporters, vulnerability
scanning, and later reverse proxy/TLS, CrowdSec, backups and optional Paperless/Onyx.
Alucard (this repository) becomes the canary and consumes the flake like a customer.

Read first, in this order: =ai/REQUIREMENTS.org= (decided requirements and marked
gaps), =AGENTS.md= (repository rules, deployment rules), =README.org=.

* Operating rules that matter here

- Questions are not authorization to edit. Interview the operator before designing
  anything the requirements leave open (see Open decisions). One question at a time.
- Workflow: =git pull --rebase=, commit, push, fast-forward the Linux checkouts
  (=/home/vincenzo/nixos-config= on dracula and alucard), build on the hosts, then
  deploy with the exact passwordless commands in =AGENTS.md=. Dracula and the Mac must
  keep building after every change: =nix eval --raw .#nixosConfigurations.<host>.config.system.build.toplevel.drvPath=
  for dracula and alucard, =.#darwinConfigurations.AC-0137.system.drvPath= for the Mac.
- New files are invisible to flake evaluation until =git add=.
- The Mac is macOS with fish and BSD sed: use python or the edit tool for rewrites.
  Commands sent over ssh run in fish on the Linux hosts; wrap bash syntax in =bash -c=.
- Read runtime logs before diagnosing; a successful evaluation proves nothing about a
  running service. Never print secrets. Decrypting with =sops -d= works on the Mac.
- Do not delete application data or retire live services without approval.
- Never enable Tailscale Funnel. Keep admin listeners private.

* Known couplings and problems to resolve during extraction

- Rule: nothing personal to the operator (accounts, the Org tree, personal paths or
  hostnames) belongs in =ai/=. The Org tree is already generalised to the optional
  =services.aiStack.sharedDirectory=; only Alucard's host config sets it, with
  =/org= as mount point. Check the rest of =ai/= and the secrets contract for leftovers.
- =ai-stack-target= was built for exclusive GPU workloads and operator tooling. Decide
  whether customers need it at all.
- =services.aiStack.user= is a required operator account; customer servers need a
  defined service/operator user model.
- =alucard/ai.nix= holds secret declarations, the =hermes.env= sops template and port
  assertions that every customer needs. Move the reusable parts into the flake behind
  one interface (secrets file path plus a few options).
- Image tags and digests in =n8n.nix=, =hermes.nix= and =container.nix= are managed by
  Renovate through regex rules in =renovate.json=; keep those rules working after the
  move and add flake-input bumps for the fleet repository.
- Alucard-only pieces that the requirements say belong in the stack and do not exist as
  reusable modules yet: reverse proxy/ACME (=hosts/alucard/services/reverse-proxy.nix=),
  CrowdSec (=hosts/alucard/security.nix=), restic backups (=hosts/alucard/backups.nix=,
  tied to a Hetzner mount and per-application jobs), Tailscale-served private ports
  (=hosts/alucard/private-access.nix=), Paperless (=modules/paperless.nix=), Onyx
  (a Docker stack on Alucard; find where it is defined before moving it).
- n8n metrics are loopback-only, so central Prometheus can scrape them for Alucard only.
- Grafana needs =grafana/secret_key= and =grafana/admin_password= in the secrets file.
  Alertmanager Telegram delivery is implemented but untested and unconfigured.
- =secrets/dracula-ai.yaml= still holds unused =grafana= and =hermes= entries.

* Design decisions already made (do not reopen without cause)

Single-tenant VPS per customer; sops-nix with one age key per host plus the operator
key; fleet repository with one small file per customer; staged updates with Alucard as
canary and operator-driven deployment; central monitoring on Alucard scraping exporters
over the tailnet; Telegram alerts; restic per customer to an operator-owned German
target; EU hosting and Requesty-only LLM egress; Hetzner x86 VPS provisioned with
nixos-anywhere and disko; presets (=basic=, =plus=) plus per-feature flags.

* Open decisions (interview the operator)

- Flake name, location and visibility (separate private repository? how does this
  repository consume it before and after the split?).
- Preset contents: what is in =basic= versus =plus=; which optional modules exist at
  launch (Paperless, Onyx).
- Deployment tool (deploy-rs or colmena) and how the canary soak period is expressed.
- n8n database: SQLite or PostgreSQL for customers.
- Public exposure details: which URL paths are allowed per application, rate limiting,
  how customer domains and ACME are configured, who manages DNS.
- Egress allow-list mechanism (nftables on the host versus provider firewall).
- How workflows and Hermes configuration are imported declaratively and what wins when
  someone edits them in the UI.
- First-run checklist: printed by the flake, or verified by a command.

* Suggested sequence

1. Interview on the open decisions above; record answers in =REQUIREMENTS.org=.
2. Define the flake's public interface: one module (=aiStack= plus feature flags and
   presets), the options customers set, the secrets contract.
3. Make =ai/= standalone inside this repository first (own =flake.nix=, outputs
   =nixosModules=, =packages=, checks), with Alucard consuming it through a path input.
   Keep all three hosts building.
4. Lift the Alucard-only pieces into reusable modules one at a time, deploying to Alucard
   after each and reading its logs.
5. Add a provisioning layer (disko layout, nixos-anywhere instructions) and a skeleton
   fleet repository with one test customer definition. Evaluate it; do not provision a
   real server without approval.
6. Split =ai/= into its own repository only when the operator says so.

* Verification expectations

Every step ends with: all three hosts evaluate and the affected ones build; flake checks
pass; the deployed Alucard has no failed units and its Prometheus targets are up.
State clearly what was only evaluated and not run.
